### p1-template-two-paths-only · discovery · _template frames the two resolution paths only — NOT the bracket TOKEN path (phase 1)

`_apply_template` is called from `_resolve_modifier` (bracket-path descent, named
table hit, free-form passthrough) and from `_resolve_selector_walk` (final return
+ last-step passthrough) — exactly the return points spec §Architecture-2 lists.
It is deliberately NOT called from `resolve_token`'s `name[sub]` branch: a
composition-order token like `mood[satisfied]` resolves a named chunk with no
modifier involved, and framing there was never decided.

Consequence for phases 4 and 5: the sticker composition order must name `mood`
PLAIN, as spec §1 transcribes it from `generate-stickers.py:49-54`. If an order
ever writes `mood[...]`, the frame silently disappears and the golden goes red
with a prompt that reads perfectly well.

### p1-template-only-layer · discovery · A _template-only dict layer (spec §1 shape) is a pure frame, and empty stays empty (phase 1)

Spec §1's config surface shows `layers: mood: {_template: "Frank's expression:
{}."}` with no table entries at all. Verified that shape works end to end: every
entry value misses the (empty) table, falls to the free-form passthrough, and
comes back framed —

    compose(["mood","scene"], {"mood": {"_template": FRAME}},
            {"mood": "sleepy", "prompt": "S"})
    -> "Frank's expression: sleepy.\n\nS"

and an entry with no `mood` field resolves to `""`, so the section is dropped
(never `"Frank's expression: ."`). Pinned by
`test_template_only_layer_is_a_pure_frame` in `tests/unit/test_compose.py`, so
phases 4 and 6 can emit that minimal layer block with confidence.

Two smaller behaviours pinned in the same group, for later phases:

- a table hit whose value is the empty string is dropped, not framed (the
  `not value` guard runs before `str.format`);
- selecting the directive key itself (`mood: "_template"`) hits the existing
  underscore guard, passes through as the literal string `_template`, and is
  then framed. The directive's VALUE never surfaces as prose — consistent with
  the pre-existing `test_underscore_keys_are_never_prose`.

### p1-mood-template-regresses-frank-covers · finding [open] · mood._template on frank shared cover layer would reframe all 84 cover prompts (phase 1)

Spec §1 puts `_template` on the layer named `mood` and says `clothing`, `mood`
and `scene` are "reused from frank's existing cover layers"; §7 has
`tools/migrate_stickers.py` emit "the `mood._template` line, for the operator to
paste into" frank's config. Read literally, that regresses every frank COVER
prompt.

Evidence (read from the live checkout `/Users/derio/Docs/projects/DERIO_NET/frank/.blog-craft.yaml`, 2026-08-03):

- `image.layers.mood` (lines 154-167) is a flat table of 13 keys whose VALUES
  already contain the whole sentence, e.g.
  `curious: Frank's expression is curious — head tilted, brow lifted, …`;
- the `hero` order (line 57) and the `banner` order (line 77) both name plain
  `mood`.

So a `_template: "Frank's expression: {}."` added to that layer frames the table
HITS as well as the sticker passthroughs, and frank's covers would compose
`Frank's expression: Frank's expression is curious — ….` — every cover, ~84
prompts. Phase 1's directive is correct and layer-name-agnostic; the collision is
in WHERE the plan declares it.

Nothing in blog-craft would catch this. Phase 5's goldens are sticker prompts
(they pass), and `tests/unit/test_image_compose.py` uses its own fixture config
with no `_template` (it passes — verified unmodified in this phase). Only frank's
own `--print-prompt` parity diff in its adoption PR would go red, i.e. after the
layer block was already pasted.

Recommended resolution for phases 4/6 (not taken here — it is a config-shape
decision, not an engine one): namespace the sticker mood layer the way spec
§Findings-2 already namespaces the other five conflicting layers —
`sticker_mood: {_template: "Frank's expression: {}."}` — and have
`composition_orders.sticker` name `sticker_mood` instead of `mood`. That also
removes the second-order hazard of a sticker whose mood text happens to equal a
cover table key (§Findings-1 notes two stickers keyed "satisfied"): under a
shared layer such a value would hit the cover table and silently compose the
cover sentence instead of the sticker's own.

`clothing` and `scene` reuse is unaffected: frank's `clothing` is a nested
two-level table, sticker clothing is free-form prose, so it passes through
unframed, and `scene` is the reserved token.

### p1-validator-forbids-literal-braces · discovery · The validator forbids ANY literal brace in _template, not just a second {} (phase 1)

`_validate_template` in `tools/validate_config.py` requires exactly one `{}` AND
exactly one `{` and one `}` overall. That is stricter than "one placeholder": it
also rejects `{0}`, `{name}`, and the `str.format` escape `{{`/`}}`. So a
`_template` cannot contain a literal brace at all.

Deliberate, and worth knowing in phase 6: the transform must not try to emit an
escaped-brace frame, and if any future frame needs a literal brace the validator
is the thing to relax (with a test), not the engine. Rationale for validating at
all is in the function docstring — a bad frame otherwise raises IndexError /
ValueError inside `generate-images.py` with a paid API call already in flight.

Non-string `_template` (including `None`, i.e. `_template:` with an empty value)
is an error too: the key being PRESENT is what triggers the check, so a
half-written directive cannot silently do nothing.

### p2-post-process-target-cwd-relative · discovery · post_process step target: paths are CWD-relative, not blog-root-relative (phase 2)

Discovered while asserting that --out skips post_process. `post_process()` passes a step target straight to PIL (`im.resize(...).save(str(s.get("target", output)))`, generate-images.py:182) with NO root join, while `output:` IS joined to the blog root (`out = root / e.get("output", ...)`). So a relative `target:` resolves against the PROCESS CWD.

In practice every real invocation runs from the blog root (frank/gondor/stoa call it via make/just from the repo top), so relative targets work by coincidence of cwd. A test that passes --config pointing at a tmp blog while cwd is elsewhere crashes with FileNotFoundError instead.

Consequence for later phases: any sticker/feature entry with post_process must either use paths that hold from the blog root or the caller must chdir. Phase 4 s generate-stickers.py shim passes --out, which skips post_process entirely, so it is not exposed. Left unfixed on purpose — fixing it changes resolution for existing configs and is out of this plan s scope.

### p2-archive-cap-prunes-its-own-count-run · finding [fixed] · archive_cap FIFO prunes the variants of its own --count run (pre-existing crash, fixed here) (phase 2)

`write_archive_entry` applies the FIFO cap (`curation.archive_cap`, default 30)
on EVERY call, globbing `<key>-*.png` and unlinking all but the newest `cap`.
A `--count N` run calls it N times for the SAME key, so once N > cap the run
deletes its own earlier variants while it is still in flight.

That was already a crash on the DEFAULT path before this phase: the contact
sheet does `Image.open(p)` for every variant, so `--count 3` with
`archive_cap: 1` died with FileNotFoundError inside PIL (pinned RED first by
`test_count_above_archive_cap_without_out_dir`). It survived in practice only
because `variants[-1]` — the one the `output:` write reads — is the newest and
therefore never pruned.

`--out` widens the exposure, because it copies EVERY variant rather than only
the last. Phase 2 therefore filters `variants` to files that still exist, warns
on stderr naming `archive_cap`, and proceeds:

    live = [(lbl, p) for lbl, p in variants if p.is_file()]

Consequences for phases 4-8:

- a sticker regen with `--count N` needs `curation.archive_cap >= N` to see all
  N candidates in the `--out` dir; below that it gets fewer plus a WARN. The
  phase 4 shim generates ONE image per key (frank's script has no `--count`), so
  it is unaffected unless the shim grows a `--count` passthrough — if it does,
  the sticker config needs an `archive_cap` at least as large.
- the archive is per-key, so the cap is per-key too: 18 stickers at one variant
  each never prune one another.

### p2-out-dir-contract-for-phase4 · discovery · The --out contract phase 4 delegates to, and the contact-sheet placement it still cannot inherit (phase 2)

Everything phase 4's `generate-stickers.py` shim needs to know about the
`--out` contract shipped here, and the one place it still diverges from frank.

**What `--out DIR` does** (`generate-images.py`, the `if variants:` block):

- `DIR/<key>.png` — always written, last variant wins. With the default
  `--count 1` that is the ONLY file, which matches frank's `regen/` dir (one
  candidate per key per run, overwritten across runs).
- `DIR/<key>-<sha12>.png` — one per variant, written ONLY when the run produced
  more than one variant. So a plain regen does not clutter the dir the operator
  eyeballs, but a `--count 3` curation run leaves all three side by side.
- the entry's `output:` is never written, and its parent dirs are never even
  created (`test_out_dir_never_creates_the_output_path`).
- `post_process` is SKIPPED entirely. Those steps write over / next to the
  PUBLISHED asset (a step `target:` is an arbitrary path), so running them for
  a candidate would clobber shipped derivatives that `--out` promised not to
  touch.
- `.regen-archive/<key>/` snapshots + `.txt` sidecars are written exactly as
  today. The sidecar still records `output: <the entry path>` — the path that
  was NOT written. Harmless (it is provenance, and it names where a chosen
  winner belongs), but do not read it as "this file was written".
- the `DIR` argument is resolved relative to the process CWD, like
  `--reference`, not relative to the blog root. The shim should pass an
  absolute path (frank's own script resolves `--out` against its script dir,
  `generate-stickers.py:89`).

**The one remaining divergence from frank — contact-sheet placement.**
blog-craft writes the curation sheet to
`.regen-archive/<key>/contact-sheet.png`, per KEY, across that key's variants,
and only when `--count > 1`. frank writes ONE sheet per RUN across all
generated keys, into the out dir, at `regen/contact-sheet.png`, whenever at
least two stickers succeeded (`generate-stickers.py:141-144`, `cols=5,
tile_width=420`). `--out` does not change sheet placement, and it cannot: the
engine's sheet is per-key by construction.

So phase 4 cannot get frank's sheet out of `generate-images.py --out` alone. It
should call `_contact_sheet(images, out, cols=5, tile_width=420)` itself from
the shim after the delegated generation (that is exactly what phase 2 task 3
parameterized it for, and the function is importable module-level), or accept
the divergence explicitly. Recommend the former; frank's README workflow points
the operator at `regen/contact-sheet.png`.

**Model fallback / timeout, same file:** `image.fallback_model` is retried when
the primary raises OR returns a response with no image part (frank's loop only
breaks on a saved image, `generate-stickers.py:133-134`), each attempt logged to
stderr with its model name. Both models failing yields `rc=1` for that key with
NOTHING written — no empty PNG, no `output:` touch. `image.timeout_ms` is
milliseconds, straight into `genai.types.HttpOptions(timeout=...)`, matching
frank's `TIMEOUT_MS = 120_000`. With neither knob set the config object stays
`None`, so cover generation is byte-for-byte unchanged.

### p2-decision6-insufficient-for-frank-sheet · finding [open] · Decision 6 alone cannot reproduce frank regen sheet: per-key-variants vs per-run-keys (phase 4 must call it) (phase 2)

Spec §Decisions 6 (and plan P2.T3) say to parameterize `_contact_sheet` "so
frank's regen contact sheet keeps its `cols=5, tile_width=420` geometry instead
of silently reflowing to 3 columns". Phase 2 did that, and it is a real
prerequisite — but it is NOT sufficient, and nothing in the spec or plan says
who supplies those arguments. Read as written, one would expect a sticker regen
through the shared engine to emit frank's sheet. It cannot.

The two sheets are different artifacts:

| | blog-craft `_contact_sheet` call site | frank `generate-stickers.py:141-144` |
|---|---|---|
| grid contents | the N variants of ONE key | the successfully generated keys of the RUN |
| how many | one per key | one per run |
| path | `.regen-archive/<key>/contact-sheet.png` | `<out>/contact-sheet.png` (i.e. `regen/`) |
| when | `--count > 1` and `curation.contact_sheet` | at least 2 keys succeeded |
| geometry | `cols=min(len,3)`, 400x260 | `cols=5, tile_width=420` |

frank's sticker run generates ONE image per key (its script has no `--count`),
so through the engine every key has a single variant and the engine's sheet is
never even produced. `--out` deliberately does not relocate the sheet: the
engine's sheet is per-key by construction and moving it would change cover
curation behavior for every blog.

Not fixed in phase 2 — the parameterization asked for is delivered and green;
the caller is phase 4's to write. Recommended resolution for phase 4: after
delegating generation with `--out`, `generate-stickers.py` calls
`_contact_sheet([(key, Image.open(regen/<key>.png)), ...], regen/contact-sheet.png,
cols=5, tile_width=420)` itself, once, over the keys it generated — the
per-run/per-key shape frank's README sends the operator to. If phase 4 instead
decides the sheet is out of scope, that is a visible behavior change for the
operator and belongs in the PR body and CHANGELOG, not in silence.

### p3-stickers-validation-semantics · discovery · features.stickers validation semantics, and why stk-4 gating must key on enabled:false rather than absence (phase 3)

The exact contract phases 4/7/8 now code and document against
(`tools/validate_config.py:_validate_stickers`, plus the two `image` keys):

- **Presence-triggered, not None-triggered.** Every check fires on the key being IN the
  mapping, matching phase 1s `_template` choice (see
  `p1-validator-forbids-literal-braces`). So a half-written `enabled:` /
  `fallback_model:` / `timeout_ms:` — YAML `None` — is an ERROR, not a silent no-op.
- **The three path keys are required exactly when `enabled is True`.** A disabled block
  may be a stub, which is what `006_to_007` seeds. `""` and whitespace-only are rejected
  (`.strip()`), and a disabled block with `prompts_file: ""` is deliberately NOT an error
  — there is nothing to generate yet.
- **`sheet` geometry is validated whenever present, enabled or not**: `dpi` / `gutter`
  positive ints, `grid` a 2-list of positive ints `[cols, rows]`, bool guarded first
  (bool is an int subclass — same shape as `image.optimize.quality`). Bad print geometry
  is nonsense regardless of the switch, and `build-sheets.py` would otherwise discover it
  at print time.
- **`sheet.size` is deliberately UNVALIDATED** — the paper vocabulary belongs to
  `build-sheets.py` (phase 4), which must reject a size it cannot lay out. See the
  companion finding.
- `image.fallback_model`: non-empty string. `image.timeout_ms`: positive int, MILLISECONDS.
  Both absent leaves pre-v7 cover generation byte-for-byte unchanged.
- Every message names the full key path and echoes the offending value.

Cross-check pinned by `test_the_v7_migration_seed_validates`: the exact dict
`006_to_007` writes validates clean, so the migration cannot produce a config its own
validator rejects. Verified end to end too — `upgrade(stoa-v1.blog-craft.yaml)` reaches
v7 with `features.stickers == {"enabled": False}` and `validate_config` returns `[]`.

**Consequence for stk-4 (phases 4 and 8).** The row reads "a blog WITHOUT
`features.stickers` gets no sticker surface". After this rung, no updated blog is without
it: gondor and stoa get `features.stickers: {enabled: false}` written into their configs
by `/update`s ladder run. So phase 4s gating test must prove the surface is absent for
**both** shapes — block absent AND `enabled: false` — and phase 8s row notes should say
"disabled" rather than "absent", or the row will read as proven by a case that no longer
occurs in the field.

### p3-sheet-block-underspecified-for-build-sheets · finding [open] · sheet: {size, dpi, grid, gutter} does not cover frank four constants — page pixels are derived and grid is hardcoded in five places (phase 3)

Spec §5 says `build-sheets.py` is a near-verbatim port "with the four hardcoded constants
(`DPI`, `A4_W/H`, `GUTTER`, the 3x3 grid) read from `features.stickers.sheet`". Read against
frank source (`frank/blog/_private/frank-stickers/build-sheets.py`, read from the HOST — the
repo is not mounted in the container), two of those four are not reads at all. Raised here
because phase 3 owns the validation of that block and deliberately chose NOT to constrain
`size` or to couple `grid` to anything.

**1. `A4_W, A4_H = 2480, 3508` (line 23) has no config key.** The spec block is
`{size: a4, dpi: 300, grid: [3, 3], gutter: 60}` — page PIXELS are absent, so phase 4 must
DERIVE them: `round(mm / 25.4 * dpi)` off a paper table (`a4 = 210x297mm` gives exactly
2480x3508 at 300, matching frank byte dimensions). Consequences:

- the derivation must be exact for a4@300 or phase 3s print acceptance (stk-3) fails
  against frank shipped sheets;
- the `size` VOCABULARY is undefined by the spec and unvalidated by
  `tools/validate_config.py` on purpose (forward-compatible: a2/letter can be added without
  a validator change). That makes it `build-sheets.py`s job to fail LOUDLY on a size it has
  no dimensions for. A silent fallback to A4 would print the wrong page.

**2. `grid: [3, 3]` is not a constant, it is a rewrite.** `3` is hardcoded in five places:
`(A4_W - 4*GUTTER)//3` and `(A4_H - 4*GUTTER)//3` (line 29), `3*cell + 2*GUTTER` (line 30),
`range(1, 10)` (line 33) and `divmod(pos - 1, 3)` (line 40). Honoring `[cols, rows]` means
`(W - (cols+1)*G)//cols`, `cols*cell + (cols-1)*G`, `range(1, cols*rows + 1)` and
`divmod(pos-1, cols)` — and the sticker `pos` field silently changes meaning (1..9 today,
1..cols*rows). The `4 *`/`2 *` gutter multipliers are `cols+1`/`cols-1` specialized to 3,
which is easy to port wrong while still producing a plausible sheet.

Recommendation for phase 4 (not taken here — it is that phase code): keep frank a4@300,
3x3, gutter 60 as the DEFAULTS so an omitted `sheet` block reproduces frank exactly, derive
page pixels from a small explicit paper table keyed by `size`, `SystemExit` on an unknown
size, and pin the generalized geometry with a non-3x3 case (e.g. `[2, 2]`) so the
`cols+1`/`cols-1` algebra is proven rather than assumed. If phase 4 instead decides only 3x3
is supported, the validator should be tightened to say so — silently accepting `grid: [2, 4]`
that the code ignores is the worse of the two outcomes.
